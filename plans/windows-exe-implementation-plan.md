## 1. 项目目标

将当前 BLE 标定交互原型落地为可在 Windows 10/11 64 位环境运行的桌面应用，连接
ZLG USBCANFD-200U，从实车 CAN 总线采集 5 节点 RSSI 和解闭锁请求，支持八方向测试、
云推参数编解码、What-if 策略重算、距离评估、统计、保存与回放。

开发阶段先使用确定性 Mock CAN 数据完成协议、会话、策略、UI、存储和打包测试；
Windows 安装包完成后再进入 CAN 盒和实车联调，降低开发过程对车辆档期的依赖。

建议按 **10 个步骤、3 个里程碑** 实施：

- 单人 MVP：约 5～6 周。
- 稳定交付版本：约 7～9 周。
- 前 9 步不依赖实车；第 10 步需要 Windows 开发机、CAN 盒和实车。

## 2. 成功标准

1. 测试人员无需 Python 环境即可安装并启动应用。
2. 应用可以稳定连接 ZLG USBCANFD-200U，并显示设备、通道和采集状态。
3. 能连续采集主、前、后、左、右 5 节点 RSSI。
4. 能从 CAN 请求信号中准确识别解锁和闭锁事件。
5. 能完成最多 8 个方向的远离闭锁、靠近解锁测试。
6. 修改基础阈值或附加策略后，8 个方向的计算结果在 200 ms 内完成刷新。
7. 图表中的动作时刻、条件满足时刻、触发节点、瞬时 RSSI、距离和统计使用同一次计算结果。
8. 云推 HEX 编码结果可被 `tools/parse_cloud.py` 正确解码，未修改字节保持不变。
9. 测试过程可保存并在没有 CAN 设备时完整回放。
10. Mock 数据能够覆盖 8 个方向并可由相同的 CAN 解码器处理。
11. 打包后通过至少 2 小时实车连续采集测试，并能在全新 Windows 电脑上安装运行。

## 4. 数据来源

数据采集和报文解码规则来源于 `tools/can_read_save.py`。

| CAN ID | 报文 | 数据 | 解码规则 |
| --- | --- | --- | --- |
| `0x629` | `IKM_MasterSt`，64B | 主节点 RSSI | `data[4] - 256` |
| `0x62A` | `IKM_NodeABSt`，64B | 前、后节点 RSSI | `data[4] - 256`、`data[28] - 256` |
| `0x62B` | `IKM_NodeCDSt`，64B | 左、右节点 RSSI | `data[4] - 256`、`data[28] - 256` |
| `0x55A` | `BLE_Req_0x55A`，32B | 解闭锁请求 | `(data[3] >> 4) & 0x0F` |

`lock_req` 取值：

- `1`：解锁请求。
- `2`：闭锁请求。

CAN 设备配置沿用脚本：

- 接口：`zlgcan`
- 设备：`ZCAN_USBCANFD_200U`
- 默认设备索引：`0`
- 默认通道：`0`
- 默认仲裁域波特率：`500000`
- 默认数据域波特率：`2000000`
- 默认启用终端电阻

### 4.1 Mock 数据

`src/ble_calibration/mock/generator.py` 使用与实车采集相同的四个 CAN ID 和字节位置，
并通过 `tools/mock_can_generate.py` 保留兼容命令，生成：

- 主、前、后、左、右 5 节点 RSSI。
- `0x55A` 闭锁请求 `2` 和解锁请求 `1`。
- 正前、右前、正右、右后、正后、左后、正左、左前 8 个方向。
- 每个方向的转身时刻、解闭锁事件时刻和模拟距离。
- 可重复的随机种子。
- 标准库即可生成的 JSONL 原始 CAN 帧。
- 安装 `python-can` 后可选生成 BLF。
- 描述方向区间、事件和生成参数的 manifest JSON。

开发和自动化测试以 JSONL 为主；BLF 用于验证正式回放链路。Mock 帧必须经过
`src/ble_calibration/can/protocol.py` 的同一套解码函数，不允许为 Mock 单独绕过协议层。
`tools/can_protocol.py` 仅作为旧脚本兼容包装。

## 5. 数据处理原则

### 5.1 时间对齐

三个 RSSI 报文分别到达，不能直接假设同一时刻同时拥有 5 个节点的新值。采集层应维护
每个节点的最新值和时间戳，按固定周期生成统一采样点。

每个采样点至少包含：

```text
relative_time
source_timestamp
master_rssi
front_rssi
rear_rssi
left_rssi
right_rssi
node_age_ms[5]
lock_req
direction
recording_state
```

节点长时间没有更新时必须标记为 stale，不能无提示地继续参与策略计算。stale 超时值应
可配置，默认值在实车联调阶段依据真实报文周期确定。

### 5.2 解闭锁事件

- 对 `0x55A` 做边沿检测，避免周期报文产生重复事件。
- 从非 `1` 变为 `1` 时记录一次实际解锁请求。
- 从非 `2` 变为 `2` 时记录一次实际闭锁请求。
- 原始 CAN 事件作为实测动作和距离基准，始终保留。
- 实线表示当前参数下策略条件开始持续满足的时刻。
- 虚线表示解闭锁动作时刻；原始参数下以 `0x55A` 为实测锚点。
- What-if 参数变化后，实线和虚线都重新计算并一起移动。
- 图上不额外叠加“实测/What-if”第三类标线。
- 瞬时 RSSI、触发节点、触发策略和实线标签均取实线时刻的数据。

### 5.3 距离锚点

测试人员输入的实际闭锁、解锁距离绑定 `0x55A` 的实车请求时刻。

应用根据实测动作时刻、实际距离和步速，把距离等级换算到图表时间轴：

```text
闭锁阶段距离(t) = 实测闭锁距离 + 步速 × (t - 实测闭锁时刻)
解锁阶段距离(t) = 实测解锁距离 - 步速 × (t - 实测解锁时刻)
```

原始参数下，优、良、差评级使用测试人员输入的实际解闭锁距离。What-if 参数变化后，
使用新虚线时刻对应的计算距离，重新计算各方向评级、闭锁/解锁优秀率和良/差方向列表。
当前参数未触发对应动作时，该方向仍计入已有实际距离的统计分母，并标记为
`差（未触发）`。

### 5.4 原始数据与派生数据分离

- 原始层：CAN 报文、报文时间戳和 BLF 文件，只追加，不修改。
- 会话层：方向、距离、步速、操作记录。
- 参数层：原始云推 HEX、解码值和 What-if 修改值。
- 派生层：条件时刻、动作时刻、触发节点、触发策略、瞬时 RSSI 和距离评级。

任何参数修改只重建派生层，确保结果可复现。

## 6. 推荐技术方案

### 6.1 技术栈

- Python：锁定经 ZLG 设备验证的 64 位版本。
- 桌面 UI：PySide6。
- 图表：pyqtgraph。
- CAN：`python-can==4.6.1` + `zlgcan==0.3.0`。
- ZLG 原生扩展：`zlgcan` 包自带的 `clgcan_driver.pyd`。
- 原始录制：python-can `BLFWriter`。
- 离线回放：python-can `BLFReader`。
- 项目数据：SQLite。
- 配置：JSON 或 TOML。
- Windows 部署：优先 `pyside6-deploy` standalone；备选 PyInstaller onedir。

和诊断，稳定后再评估单文件发布。

## 10. 主要风险及对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| ZLG 驱动、DLL、Python 架构不一致 | EXE 无法打开设备 | 固定 64 位版本矩阵，在目标 Windows 构建和验证 |
| ZLG 动态库不能直接打包分发 | 安装包缺依赖 | 提前确认授权；必要时提供独立驱动/library 安装步骤 |
| 三个 RSSI 报文不同步 | 计算使用不同时刻数据 | 最新值缓存、节点年龄、stale 标记和黄金数据验证 |
| 策略描述与 ECU 真实实现存在差异 | What-if 结果不可信 | 使用黄金 BLF 和 ECU 请求逐条对比，建立差异用例 |
| UI 绘图影响 CAN 接收 | 丢帧或事件延迟 | CAN 独立线程、环形缓冲区、UI 限帧刷新 |
| 单文件打包导致 DLL 路径变化 | 设备库加载失败 | 首版使用 standalone/onedir，再评估 onefile |
| 缺少实车或 CAN 盒 | 不影响前 9 步，但可能延误正式发布 | 使用确定性 Mock 完成开发，打包后集中进行硬件和实车验收 |
| BLF 文件过大 | 磁盘耗尽 | 保留分卷机制、显示磁盘空间并提供录制目录配置 |

## 11. 已确认事项与后续验证

已确认：

1. 目标系统为 Windows 10/11 64 位。
2. CAN 依赖为 `python-can==4.6.1`、`zlgcan==0.3.0`，原生扩展使用包内
   `clgcan_driver.pyd`。
3. `0x55A` 的 `1/2` 直接作为实测解锁/闭锁动作时刻。
4. 两个实际距离分别绑定 `0x55A` 的实际闭锁、解锁时刻。
5. 实线为条件开始满足时刻，虚线为动作时刻；What-if 修改后两者一起移动。
6. 测试人员手动开始和结束；实际解锁后继续记录，事件或距离不全时保存为不完整方向。
7. Mock 覆盖节点超时、报文乱序、重复请求和完全不触发。

不阻塞第二步、在对应阶段验证：

1. 每个 RSSI 报文的实车周期、设备时间戳行为和 stale 超时最终值。
2. Windows 打包所用 CPython 版本与 `clgcan_driver.pyd` ABI 是否一致。
3. ZLG 系统驱动版本、VC++ Runtime 和干净电脑安装步骤。
4. BLF 是否随项目复制、首版是否增加 CSV/图片导出等次要产品选择。
